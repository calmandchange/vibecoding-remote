# 语音输入延迟实测（2026-10-10）

测试环境：当前 Windows 电脑、已配对 Android 测试机、微信输入法、VB-CABLE。数字只代表这套设备与当前网络状态，界面视觉时刻含约 25 ms 的采样粒度。

| 阶段 | 实测 | 测量方式 |
| --- | ---: | --- |
| 手机触摸到电脑执行 `Ctrl+Win` | 中位数约 19 ms；10 次为 17–64 ms | 手机日志、Windows 接收日志的时间戳；ADB 持续 shell 校时，约 ±11 ms 不确定度 |
| 手机触摸到首帧声音到电脑 | 约 97–118 ms | Android 首帧日志加电脑首帧日志；与上项同一批 10 次 |
| 直接在电脑触发到微信语音提示出现 | 约 539 ms | 完全绕开手机和蓝牙，截图像素每 25 ms 采样；单次视觉测试 |
| 直接在电脑触发到微信识别中的文字首次可见 | 约 1310 ms | 同上，单次视觉测试 |
| 固定语音的末尾到完整文字进入输入框 | 约 1.1–1.8 秒 | 电脑直接向 VB-CABLE 播放同一段语音，3 次；以末尾有声采样估算 |
| 松开电脑快捷键到完整文字进入输入框 | 约 0.9–1.6 秒 | 同上，3 次 |
| 本地流式识别，末尾有声采样到最终结果 | 约 0.15–0.19 秒 | sherpa-onnx 2025 中文 Zipformer int8，电脑实时分帧喂入同一语音，3 次 |

## 结论

蓝牙控制链路一般只占几十毫秒，音频到电脑也约 0.1 秒；真正影响体感的是微信语音界面启动和转写后的提交阶段。即使改用 Wi-Fi 或 USB，后两段仍存在。把音频链路整体重做成 Wi-Fi 并不是最有效的第一步。

电脑本地流式识别有明显的速度潜力：新模型在固定中文句子“今天我们测试语音输入的响应速度”上三次均识别正确（未自动补标点），说完后约 0.15–0.19 秒形成最终文本；另一句中文指令也识别正确。技术英文句子中 `VibeCoding` 被识别为 `YCODIN`，说明它目前还不能无条件替代微信输入法。模型首次加载约 5.6 秒，因此接收程序启动时常驻加载。可切换的“极速本地识别”模式现已接入 Windows 接收程序：保留手机蓝牙麦克风及按键，电脑接收音频后直接调用流式识别并将结果输入当前光标位置，跳过微信语音界面和 VB-CABLE。用固定中文语音实测，末尾有声采样到 Windows 输入框出现完整文字约 0.19 秒；实际真人语音仍需体验和质量评估。

## 其他可行路线

| 路线 | 对本次瓶颈的作用 | 当前状态 |
| --- | --- | --- |
| 蓝牙音频 + 电脑本地流式识别 | 直接移除微信启动与提交等待 | 已实现可切换试用模式，中文固定语音通过 |
| 手机本地识别，只通过蓝牙传文字 | 也能移除微信等待，并减少蓝牙音频流量；受手机算力、发热与模型质量影响 | [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx) 提供 Android 支持；尚未对这台手机测速 |
| Wi-Fi/USB 传音 + 微信输入法 | 最多影响首帧到达电脑的约 0.1 秒，微信自身的约 0.54 秒启动和 0.9–1.6 秒提交仍在 | 当前不优先改造 |
| 换另一个本地中文识别模型 | 可改善专有词、英文和标点，但需重新实测速度与准确度 | [FunASR](https://github.com/modelscope/FunASR) 等为后续候选，未测 |

## 复现

- `measure_link.py`：要求 Android 手机通过 USB ADB 连接、App 在前台、蓝牙电脑接收程序已运行。会模拟 10 次按住手机按钮并保存 `results/bluetooth-link.json`。校时采用一个持续运行的 `adb shell -T`，选择往返时间最短的样本；报告的约 ±11 ms 是往返时间的一半，只表示时钟偏差的保守界，不含 Android 日志写入调度误差。
- `native_target.ps1` + `inject_speech.py`：创建独立输入框，用 Windows 自带中文 TTS 生成的固定 WAV 直接模拟语音输入，绕过手机/蓝牙。结果在 `results/run*-target.jsonl` 和 `results/run*-injection.jsonl`。微信输入法的语音提示视觉采样结果在 `results/visual-target.jsonl`。
- `measure_local_asr.py`：从同一 WAV 读取 16 kHz PCM，按真实时间每 20 ms 喂入模型。`results/local-asr-2025.json`、`local-asr-command.json` 和 `local-asr-technical.json` 保留了结果。使用的模型为 [sherpa-onnx 官方中文流式 Zipformer](https://github.com/k2-fsa/sherpa-onnx/releases/download/asr-models/sherpa-onnx-streaming-zipformer-zh-int8-2025-06-30.tar.bz2)；运行前需安装 `sherpa-onnx`、`sherpa-onnx-bin` 和 `numpy`，并将模型放到 `pc/models/`。
- `test_local_delivery.py`：同一段 WAV 走本地识别和 Windows `SendInput`，注入到临时输入框；`results/local-delivery.json` 记录了识别器输出、实际输入框文字和 0.19 秒的末尾到入框耗时。
- `test_phone_local.py`：手机按钮通过真实蓝牙链路驱动本地模式；静音环境中识别为空，日志确认了音频接收与 93 ms 的松手后解码耗时。

固定 TTS 语音、真实手机按键和本地模型测试了链路及识别引擎，但没有覆盖真人语速、不同噪声环境和多型号手机。微信的视觉启动时间仅测了一次；文字提交延迟复测了三次。本地输入框试验中已包含文字注入耗时，但没有把手机真人说话、蓝牙和本地输入串成完整的有声测试。
